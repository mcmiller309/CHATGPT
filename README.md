# Royalls Studio Lighting Controller

A cinematic React/Vite/TypeScript dashboard for studio lighting. Version 2 preserves the Version 1 virtual studio, presets, brightness, Flash/Pulse/Blackout, saved gift mappings, test gifts, and activity log, and adds a local Node.js Philips Hue API v2 backend. **Every page load starts in simulation mode.** TikFinity is not implemented. Test gifts are generated by the dashboard, not received from TikTok.

## Mac installation

Use Node.js **24 LTS** (Apple Silicon supported), or a current Node 22 release >=22.13. From Terminal:

```sh
git clone https://github.com/mcmiller309/CHATGPT.git
cd CHATGPT
npm ci
cp .env.example .env
chmod 600 .env
```

For an existing checkout, use its folder instead of cloning again. Edit `.env` locally with a trusted editor:

```dotenv
HUE_BRIDGE_IP=192.168.1.249
HUE_APPLICATION_KEY=your-existing-hue-application-key
HUE_CA_CERT_PATH=/absolute/path/to/trusted-hue-ca.pem
HUE_BRIDGE_ID=your-16-hex-digit-bridge-id
```

The placeholder values above are not working credentials. Do not paste your actual key into chat, screenshots, shell commands, GitHub, frontend code, or `VITE_*` variables. `.env` and `.env.*` are Git-ignored; only the empty `.env.example` is tracked. Node loads `.env` into the backend process; Vite does not receive the key through its client variable mechanism. No configuration endpoint returns it, and upstream error details are not logged or returned.

## Verified Hue HTTPS

Hue bridges use a Hue certificate chain rather than a normal public web certificate. Obtain the trusted Hue root CA PEM using the official [Hue HTTPS guidance](https://developers.meethue.com/develop/application-design-guidance/using-https/) over verified HTTPS. Verify its provenance before installing it; store it outside the repository. Supply the bridge's 16-hex-digit ID from a trusted bridge/administration source. The backend connects to the configured private IPv4 address, verifies the certificate chain with the supplied CA, and uses the lowercase bridge ID as the TLS server name for normal Node hostname verification.

Certificate or bridge-ID mismatch **fails closed** in development and production. Never use `NODE_TLS_REJECT_UNAUTHORIZED=0`, `rejectUnauthorized: false`, or blindly trust a certificate collected from an unauthenticated network connection. The server refuses to start with the TLS-disable environment switch. Certificate/firmware problems need correction rather than a verification bypass. The CA and bridge ID are required in addition to the existing application key. Keep the Mac on the bridge's local network; the Codex cloud machine normally cannot reach that LAN.

## Preview and run

Simulation needs no Hue configuration or backend:

```sh
npm run dev
```

Open http://127.0.0.1:5173 on your Mac. For Hue development, run this in a **second terminal** in the project folder:

```sh
npm run backend:dev
```

Use the exact `127.0.0.1` address, not `localhost`. Vite uses fixed port 5173 and proxies `/api` to the loopback backend on 3001. Do not expose either server through LAN binding, a public tunnel, or a reverse proxy.

For the production dashboard and backend together:

```sh
npm run build
npm run backend
```

Open http://127.0.0.1:3001 on your Mac. The backend serves only production HTML/JS/CSS from `dist` and the local API. `npm run preview` is still available for simulation-only production UI preview; it has no Hue API proxy. Press Control-C to stop each server. Start from the project root so `.env` and `dist` resolve correctly.

## Read-only connectivity check

Click **Check bridge & discover lights**. This authenticates a read-only Hue API v2 `GET /clip/v2/resource/light`, verifies TLS, and lists names and supported actions. It sends no PUT and changes no lights. Failure messages point to local configuration, bridge authentication, certificate trust, ID, and connectivity without disclosing the key. No automatic discovery, polling, or lighting command runs on startup.

Select a device. Changing the selection does not change any physical lights. The selector is locked during live mode; return to simulation before choosing another light.

## Physical control — explicit opt-in

Only do this when you intentionally want to change real lighting:

1. Discover lights and select one device.
2. Click **Enable live mode** and read the warning.
3. Click **I confirm — enable physical control**. This arms a short-lived backend session but sends no light command.
4. Subsequent color, brightness, effect, and **Send test gift** actions affect that selected physical light through the backend.

No development or automated test in this project requires physical control. Do not enable live mode merely to test installation.

Live color presets use Hue XY coordinates (the bridge clamps to its gamut). Warm white uses 370 mirek, clamped to the device's declared limits. Brightness is committed on slider release or keyboard adjustment; zero turns off. Blackout sends `on: false`. Flash uses the bridge-native `on_off` signaling effect bounded to 2.4 seconds. Pulse uses native `breathe` only if the light advertises that effect. Unsupported controls are disabled, including unsupported gift assignments; the backend independently rechecks capabilities before each write. Pulse is not emulated with an indefinite polling/flash loop. Standard color/brightness commands clear native effects when `no_effect` is supported.

The studio rendering is a **command preview**, not measured real-time light state. The log records bridge acceptance, not proof of physical illumination. Hue errors return the UI to simulation and request session disarming. An in-flight command already submitted to the bridge cannot be undone. Returning to simulation sends no lighting write and does not restore the previous light state or stop an already running native effect. Choose an appropriate supported steady-color command while live if you need to stop an effect. Flash can affect photosensitive people; use intentionally.

Simulation Flash lasts 2.4 seconds; simulation Pulse continues until another command. Browser reduced-motion preferences disable preview animations; this does **not** prevent physical effects in live mode. Gift mappings are saved in browser storage. Activity history is session-only (latest 50 events). Live authorization and credentials are never stored in browser storage. Refresh always returns to simulation.

## Local API protections and limitations

- Node's built-in HTTP server binds only to `127.0.0.1:3001`.
- Exact Host, browser Origin, Fetch Metadata, and a required custom header protect against DNS rebinding and unauthorized cross-origin browser requests. No CORS access is granted. Production permits only the backend origin; development additionally permits the fixed Vite origin.
- Same-origin UI bootstraps a cryptographically random in-memory bearer session; protected endpoints require it. Tokens expire after 15 minutes; the UI disarms proactively after 14 minutes in live mode. Explicit confirmation is required server-side before writes.
- API requests are limited globally to 120/minute; commands are serialized and at least 800ms apart globally. Session count and request-body size are bounded. Device IDs, brightness, actions, capabilities and JSON bodies are validated.
- All bridge writes target discovered light UUIDs under `/clip/v2/resource/light`; browser input cannot choose bridge hosts or arbitrary URLs. HTTPS redirects are rejected. Bridge requests time out after five seconds.
- Production static responses use CSP, frame protection, MIME protection, and no-store headers. Error responses are generic and never serialize raw upstream errors or configuration.

These controls protect against other websites, not malicious local software, browser extensions, a compromised user account, or same-origin injected code. A local process can bootstrap its own session. This is a single-user local application; it must not be publicly hosted without a stronger authentication/deployment design. Hue's application key may itself allow broader access on the bridge than this app exposes; protect and revoke it using Hue administration if leaked. Credentials remain readable to your OS account and backend process. There is no remote authentication or cloud credential storage.

## Tests and security audit

```sh
npm test
npm run build
npm audit
```

Tests cover simulation behavior and persistence, live confirmation and gift routing, capability checks, request validation, origin/host rejection, sessions, expiry, rate limiting, disarming during discovery, sanitized errors, and secure TLS request options. **All Hue responses and writes are mocked. No tests contact the configured bridge or change physical lights.** A real Mac-to-bridge TLS/read-only discovery check must still be performed with your local `.env`.

The initial dependency audit found Vitest/@vitest/mocker path traversal/arbitrary-file-read vulnerabilities ([GHSA-82fw-gwwq-j7x9](https://github.com/advisories/GHSA-82fw-gwwq-j7x9)) and Tinypool prototype-pollution/RCE gadgets ([GHSA-5gmw-xhrv-c9v3](https://github.com/advisories/GHSA-5gmw-xhrv-c9v3), [GHSA-85c8-ppgw-ccpr](https://github.com/advisories/GHSA-85c8-ppgw-ccpr)). These were development-tool dependencies, not deployed Hue backend dependencies. Updated Vitest and the compatible Vite/React plugin toolchain; the resulting `npm audit` reports zero known vulnerabilities at implementation time. This does not prove absence of undiscovered vulnerabilities. Never run untrusted tests or expose development/test servers publicly.

## Structure and future integrations

- `src/controller.ts`: pure simulation state and gift mapping types.
- `src/hue.ts`: local API transport; receives no bridge credentials.
- `src/App.tsx`: dashboard, mode confirmation, device selector, gift routing and activity.
- `server/app.mjs`: loopback API, session/mode/security rules and production static serving.
- `server/hue.mjs`: verified HTTPS Hue v2 adapter, payload translation and capability checks.
- `server/index.mjs`: backend startup using Node's `.env` loader.

A future TikFinity integration should validate events in this backend and map allowlisted actions; it is not implemented here. Home Assistant is also not implemented. Never connect a browser directly to Hue with an application key.
